# 开发计划 · 写作规则

本目录（`plans/`）管理**开发计划**。与 `progress/_开发日志规范.md` 的分工一句话说清：

> **日志回答「今天实际发生了什么」；计划回答「接下来准备怎么做、为什么这么做」。**

## 什么才算一个计划文件（最重要的原则）

**不要所有 TODO 都建计划文件。**

以下这类完全没必要单独建计划（记进日志即可）：

- 修一个按钮颜色
- 升级一个 npm 包
- 删两个死文件
- 同步一次远端分支

真正适合建计划文件的是这种事情：

- 跨模块解耦（如 orchestrator 与某服务的硬耦合）
- 大文件/大模块拆分
- 生成系统这类核心链路的重构
- 支付/计费模块实施
- 平台级迁移

因为这些事情往往：**不是一天完成 + 涉及多个步骤 + 存在设计决策 + 实施过程中计划会变化**。

## 命名与结构

- 文件名：`YYYY-MM-DD-主题.md`，日期为**立计划那天**（不是预计完成日）
- 计划是活文档：设计决策变化时直接改文件内容，并在文末「变更记录」补一行；不需要为变化新开文件
- 完成后：顶部状态改为 `已完成`，文末补「结果」一段（做了什么、偏离计划的部分、验证方式），日志当天条目用 `[[../progress/YYYY-MM-DD]]` 指过来

## 文件模板

```md
# 计划 · <主题>

状态：调研中 / 进行中 / 暂停 / 已完成 / 已废弃
立项：YYYY-MM-DD　最近更新：YYYY-MM-DD

## 背景与 Why
为什么做这件事，不做的代价是什么。

## 目标与非目标
要达成什么；明确不做什么（防止范围膨胀）。

## 关键设计决策
列出决策点、候选方案、倾向与理由。这是计划文件最有价值的部分。

## 步骤草案
按里程碑拆，每步可独立验证。

## 验收标准
怎么判断做完了。

## 变更记录
- YYYY-MM-DD 立项
```
